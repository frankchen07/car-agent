# WRX Agent

AI mechanic advisor for Frank's 2003 Subaru Impreza WRX. Knows the car's full service history, maintenance schedule, and OEM specs — queryable via CLI or Telegram.

---

## What it does

- **Manual search** — semantic search over the WRX shop manuals and service docs (PDFs → embedded chunks)
- **Service history** — query logged service events by date, mileage, or keyword
- **Maintenance plan** — get overdue and upcoming service items based on current odometer
- **Issue tracking** — log and retrieve problems, symptoms, and DTC codes

Two interfaces: a CLI REPL for local dev, a Telegram bot for mobile use.

---

## Architecture

```
  CLI (src/cli.py)          Telegram (src/bot.py)
        │                          │
        └──────────┬───────────────┘
                   ▼
         Agent Graph (src/agent.py)
         LangGraph ReAct loop
                   │
         ┌─────────┼─────────────────┐
         ▼         ▼                 ▼
    ask_manual  get_service_history  log_issue / get_issues
    log_service get_maintenance_plan
         │         │
         ▼         ▼
  evidence_index  Postgres (pgvector)
  .jsonl + cosine  vehicles / service_events /
  similarity       maintenance_rules / oem_parts / issues
         ▲
  Knowledge Pipeline
  (7 stages: ingest → classify → chunk →
   summarize → extract → assemble → report)
         ▲
  knowledge/sources/
  (manuals/, receipts/, ownership/, placeholders/)
```

## Setup

### Prerequisites

- Python 3.11+
- Docker Desktop

### 1. Create virtualenv and install

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

### 2. Configure environment

```bash
cp .env.example .env
```

Edit `.env` and fill in at minimum:

```
DATABASE_URL=postgresql://car:car@localhost:5433/car
CHAT_PROVIDER=anthropic          # or: openrouter, openai
CHAT_MODEL=claude-sonnet-4-6-20250514
ANTHROPIC_API_KEY=sk-ant-...     # whichever provider you chose
```

For the Telegram bot, also add:
```
TELEGRAM_BOT_TOKEN=              # from @BotFather
TELEGRAM_ALLOWED_USERS=          # your Telegram chat ID (leave blank for open)
```

### 3. Start Postgres

```bash
docker compose up -d
```

### 4. Apply schema

```bash
python migrations/apply.py
```

### 5. Seed the database

```bash
python scripts/seed_db.py
```

Loads `knowledge/sources/canonical/` CSVs into the vehicles, service_events, maintenance_rules, and oem_parts tables. Safe to re-run — truncates and reloads.

### 6. Run the knowledge pipeline (optional — needed for manual search)

```bash
cd knowledge
python run_pipeline.py --config config/wrx.yaml
```

This processes PDFs in `knowledge/sources/` through 7 stages and produces:
- `output/wrx/evidence_index.jsonl` — embedded chunks (used by `ask_manual`)
- `output/wrx/runtime_context.md` — summary injected into the agent's system prompt

Pipeline takes ~10–30 min depending on source volume. LLM-heavy stages are 4 and 5.

3. Find your chat ID by messaging `@userinfobot`, then set `TELEGRAM_ALLOWED_USERS`
4. Run:

```bash
source .venv/bin/activate

```

Bot commands:
- `/start` — greeting and help
- `/mileage 154000` — update odometer for this session
- `/reset` — clear conversation history

## Knowledge pipeline

### Adding documents

Drop files into `knowledge/sources/` in the appropriate subdirectory:

| Dir | Contents | Pipeline tier |
|---|---|---|
| `manuals/` | OEM shop manuals, technical service bulletins (PDF) | primary |
| `receipts/` | Service receipts, invoices (PDF) | secondary |
| `ownership/` | Title, registration, warranty docs (PDF) | secondary |
| `placeholders/` | Stubs for missing docs | secondary |

Then re-run the pipeline:

```bash
cd knowledge
python run_pipeline.py --config config/wrx.yaml
```

**Flags:**
- `--from-stage 4` — resume from stage 4 (skip re-ingesting)
- `--only-stage 6` — run only one stage
- `--force` — reprocess even unchanged files

**Note:** `knowledge/sources/manuals/` etc. are gitignored (large/personal). `knowledge/sources/canonical/` (CSVs) is tracked.

### Pipeline stages

| Stage | What it does |
|---|---|
| 1 — Ingest | Parse files, compute content hash, count tokens, flag duplicates |
| 2 — Classify | Assign tier (primary/secondary) by filename pattern, LLM fallback |
| 3 — Chunk | Split into ~500-token semantic chunks |
| 4 — Summarize | Per-source LLM summaries (cached — skipped if source unchanged) |
| 5 — Extract | Cross-source synthesis: doctrine, key facts, diagnostics |
| 6 — Assemble | Build `evidence_index.jsonl` (with embeddings) + `runtime_context.md` |
| 7 — Report | Token budget, duplicate flags, QA metrics |

## Design decisions

**1. LangGraph ReAct loop**

Chose LangGraph over a hand-rolled tool loop. The alternative was a simple while-loop calling the Anthropic SDK directly and parsing `stop_reason == "tool_use"` manually. LangGraph gives us a proper graph with named nodes, conditional routing, and a `ToolNode` that handles all the tool dispatch boilerplate. More importantly, it integrates natively with LangChain's chat model abstraction, which was the prerequisite for provider-swapping (#2).

**2. Provider abstraction via `CHAT_PROVIDER` env var**

The agent started with raw Anthropic SDK calls. We refactored to LangChain's `ChatAnthropic` / `ChatOpenAI` so the provider is a config concern, not a code concern. Switching to OpenRouter (cheaper, same Claude models) is a one-line `.env` change. The tool-calling interface — `AIMessage.tool_calls` — is normalized by LangChain across providers, so the routing logic in `agent.py` doesn't change between providers.

**3. Local JSONL + cosine similarity for manual search**

The alternative was a hosted vector DB (Pinecone, pgvector, etc.). We skipped it. The knowledge base is ~55 PDFs, `all-MiniLM-L6-v2` embeddings fit in memory, and cosine similarity over a few thousand chunks takes milliseconds. Adding a vector DB service would mean another infra dependency, another secret to manage, and another thing to break. The JSONL approach also means the evidence index is just a file you can inspect or grep.

**4. `asyncio.to_thread` for Telegram bot**

`python-telegram-bot` is fully async; LangGraph's `graph.invoke` is sync. If we called `invoke` directly from an async handler, it would block the entire event loop — the bot would stop responding to all Telegram messages while one agent call was running. `asyncio.to_thread` runs the sync call in a thread pool, keeping the event loop free. This matters even for a single-user bot since Telegram can deliver messages faster than the agent processes them.

**5. In-memory per-chat state**

Each Telegram chat gets its own conversation history and mileage stored in plain Python dicts, keyed by `chat_id`. We considered persisting to Postgres (LangGraph supports checkpointing), but for a personal bot that runs on one machine, the complexity isn't worth it. The main downside: bot restart clears context. The workaround is `/reset` — explicit, intentional, and good enough for now.

**6. Lazy-loaded graph singleton**

`build_graph()` triggers LLM client initialization and loads the sentence-transformer model into memory (~90MB). If this happened at import time, the bot module would be slow to import and would fail loudly if env vars weren't set yet. The `_get_graph()` singleton pattern defers initialization to the first actual message, which also makes testing and dev easier since importing `src.bot` doesn't immediately hit the network or disk.

**7. `TELEGRAM_ALLOWED_USERS` access control**

Telegram bot tokens, if they leak, let anyone message your bot. Since the bot has write access to the database (can log service events and issues), open access is a real risk. `TELEGRAM_ALLOWED_USERS` is a comma-separated list of chat IDs that acts as a simple allowlist. Empty = open, which is fine for local testing or if you trust the token stays private. Your chat ID is easy to get via `@userinfobot`.

**8. Source file layout and gitignore strategy**

Raw PDFs live in `knowledge/sources/manuals/`, `receipts/`, etc. — gitignored because they're large, personal, and not useful to version (they're rebuilt from originals). The canonical CSVs in `knowledge/sources/canonical/` are the structured source of truth for service history, maintenance plan, and OEM parts — small, diffable, worth tracking. Ignoring specific subdirs rather than the whole `sources/` parent is what lets `canonical/` be tracked while keeping everything else out.

**9. System prompt assembled at graph build time**

`SOUL.md` (static persona) and `runtime_context.md` (generated by the knowledge pipeline) are concatenated once when `build_graph()` is called, not on every turn. This avoids a file read on every message. The tradeoff: if you re-run the pipeline while the bot is running, it won't pick up the new `runtime_context.md` until restart. Acceptable — pipeline runs are intentional, infrequent, manual operations.

**10. Postgres on host port 5433**

Port 5432 is what most dev machines already have Postgres running on. Mapping the container to 5433 avoids a silent conflict where `docker compose up` succeeds but the app connects to the wrong Postgres instance. Nothing clever — just a collision-avoidance default that saves a confusing debugging session.

**11. CLI + Telegram as dual interfaces**

The CLI (`python -m src.cli`) is the development interface — fast feedback loop, no external dependencies, easy to test specific queries. The Telegram bot is the production interface — usable from a phone while standing next to the car. Both wrap the same `build_graph()` call, so they stay in sync automatically. Adding more interfaces (web, Slack, etc.) follows the same pattern: implement the transport layer, call `build_graph()`.

**12. Idempotent seed script**

`scripts/seed_db.py` truncates all tables before loading. The alternative — checking for existing rows and upserting — is more complex and can leave stale data if CSV rows are removed. Since the CSV files are the source of truth and the database is entirely derived from them, a clean reload is always safe. The `RESTART IDENTITY` resets serial IDs so re-seeds produce deterministic results.
